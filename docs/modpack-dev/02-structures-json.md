# 02 结构（优先用扫描器）：机器长什么样（从方块堆到可识别结构）

这一章优先教你用 **结构扫描器** 生成结构文件（开发期最省心、最不容易写错）。

你可以把结构理解成：

- 机器控制器旁边**应该摆哪些方块**，摆成什么形状。
- 玩家搭对了，机器就“成型”；搭错了就不工作。

## 1. 结构文件放哪

- `config/prototypemachinery/structures/`
- 可以有子文件夹，PM 会递归扫描。

## 2. 结构 ID（最重要的字段）

结构 JSON 里会有一个 `id`，它就是你在脚本里 `m.structure("...")` 要填的值。

建议格式：`my_pack:machine_name`。

## 3. 最推荐的做法：用扫描器导出结构（然后只手改少量字段）

开发期建议流程：

1) 在创造模式搭一个“能成型的最小版本”（先用最普通的方块堆起来）
2) 用 **Scanner Instrument（扫描器）** 框选机器结构范围
3) 在扫描器 GUI 里导出结构 JSON
4) 只做必要的手工改动（通常只改：`id`、显示名称、少量方块规则）

这样做的好处：

- 结构形状不容易写错（少掉 90% 的手写坐标错误）
- 后续你只需要“增量修改”，而不是从零维护一份巨大的 JSON

## 4. 兜底方案：从 0 到 1 手写一个“最小结构”

推荐先用最简单的结构跑通：

- 控制器旁边 1 个铁块

然后你再慢慢加：输入仓、输出仓、能量仓、装饰方块等。

> 再强调一次：除非你在写“模板结构/教学样例”，否则优先用扫描器导出，然后小改。

## 6. 常见坑

### A. 文件放错位置

- 放在 `src/main/resources` 是开发者写模组的路径；整合包应该放 `config/...`。

### B. 结构 id 重复

同一个 id 出现在多个 JSON，PM 会提示重复并忽略其中一个。

### C. 方块状态太“苛刻”

如果你写死了 meta 或 NBT，很容易让玩家搭不出来。

建议：

- 先宽松（只要求方块类型）
- 再逐步加严（例如必须是某种朝向/必须带某个方块实体数据）

## 7. 结构热重载（开发期）

PM 已提供结构热重载命令，适合在你反复调整结构 JSON 的开发期使用。

### A. 命令

- `/pm_structures reload`

### B. 它会做什么

1) **服务端**从磁盘重新读取：
	 - `config/prototypemachinery/structures/` 下的所有结构 JSON
	 - 并用新内容替换结构注册表

2) 然后服务端会通知**客户端**执行一次“本地磁盘重载”，并清理结构预览缓存。

### C. 多人/整合包发布时要注意

客户端重载是“从自己的磁盘读”，所以：

- 单人（集成服务器）基本不会踩坑
- 多人服务器需要确保 **服务端与所有客户端** 的结构文件一致，否则：
	- 客户端的预览/提示可能与服务端不同
	- 你排错会很痛苦（看起来像“鬼畜不同步”）

### D. 已经放在世界里的机器会怎样？

一般来说，热重载主要用于：

- 你调整结构规则/摆法后，马上验证“新结构能不能成型”

对**已经成型**且已经放在世界里的机器：

- 具体效果取决于该机器何时触发“重新校验结构”（有些机器会周期性检查/或在关键事件时检查）
- 最稳妥的做法是：在调试阶段直接**拆掉并重新放置控制器**，确保走一遍全流程
